1.调用模型Qwen3-30B-A3B-Base
2.专家调度上注意在cpu上存储每层一半专家，因为要实验低内存场景。
3.草稿模型采用下面调度算法
4.在推理中记录数据，并调用/data2/group_谈海生/lagin/models/SRDP_Experiments/run_soft_20260128_231323/best_model.pth判断是否继续生成

完整调度算法如下：
设定n = 2（即 CPU 最多只能算 2 个专家，GPU 至少算 6 个）。Router 输出了该层所有 64 个专家的打分概率。
1.	初始 Top-8 划分：
找到概率最高的 8 个专家。假设其中有 3 个在 CPU，5 个在 GPU。
o	$S_{cpu\_needed}$ = 3 个
o	$S_{gpu\_needed}$ = 5 个
2.	并行资源判定与截断：
因为 $3 > 2$，触发延迟保护机制。
o	CPU 截断：在 $S_{cpu\_needed}$ 的 3 个专家中，只保留概率最高的2个，丢弃另外 1 个。现在 CPU 任务 = 2。
o	GPU 替补：GPU 原本只需要算 5 个，现在还要帮忙补 1 个名额（凑齐 8 个）。怎么补？不要随机。直接在 Router 打分排名第 9、第 10、第 11... 的专家中，挑出 1个正好存放在 GPU 上的专家。
3.	权重重归一化 (Renormalize)：
因为替补的专家原本概率较低，为了保证输出尺度一致，把最终选定的这 8 个专家2 个 CPU + 6 个 GPU）的权重重新进行 Softmax 归一化，使其和为 1。
4.	异构并行执行：
o	GPU 流：启动 6 个专家的并行推理。
o	CPU 流：通过 PCIe 异步拉取隐藏状态（Hidden State，通常只有几 KB，传输极快），由 CPU 执行那2 个最高优 CPU 专家的推理。
o	合并：CPU 将算好的结果传回 GPU VRAM，与 GPU 的6 个结果按权重相加（Reduce Sum）。





Target是否采用cpu算力
不论是草稿模型 (Draft) 还是原模型 (Target)，它们底层的专家物理位置都是固定的。但它们的点单策略不同：
•	Target 模型（原模型验证）： 严格按照顾客要求（Router 打分），该谁做就谁做。如果顾客点了 3 个 CPU 专家的菜，GPU 就会老老实实把 3 张纸条传给 CPU，等 CPU 慢慢把 3 道菜做完送回来。（保精度）
•	Draft 模型（草稿生成）： 追求极致速度（你设计的 $n=2$ 算法）。如果顾客点了 3 个 CPU 专家的菜，大堂经理一看 CPU 厨房忙不过来（超过了限制的 2 个），就会直接划掉第 3 个菜，强行让闲着的 GPU 厨房用 GPU 上的专家随便炒一个概率高的“替补菜”顶上。（保延迟）
